Notes on the raw run:

- `agent_replies` counts every reply the agent posted, including the reply to
  the first "conversation started" message, which is why it is a little higher
  than `messages received` at small N.
- `ws_connect_failures_total`: 0, 0, 1 and 8 for N = 10, 50, 100, 200. A
  visitor that fails before the handshake (conversation or socket ticket fails)
  does not add a connect sample, so the "connect success" denominator is the
  number of handshakes that were actually attempted, not `N + M`.

## Observed degradation point

The stack is healthy up to N = 50: every handshake succeeds, no HTTP error is
returned, and p95 round-trip stays under 2 seconds. Degradation starts between
N = 50 and N = 100 and is a cliff at N = 200.

- At N = 100 the agent side cannot keep up: 1390 visitor messages are posted but
  only 30 client replies go out and the visitors receive 13 of them. The few
  replies that do arrive are very late, so p95/p99 for both round trips jump to
  8–14 seconds while p50 stays low. 37 requests (2.24%) fail with HTTP 5xx.
- At N = 200 the run collapses: 91 of 101 handshakes succeed, 111 requests
  (6.0%) return HTTP 5xx and no agent reply is ever delivered, so no round-trip
  sample is recorded at all.

The server log for the N = 200 run shows the cause of the 5xx errors:

```
psycopg2.OperationalError: connection to server at "db" (172.20.0.3), port 5432
failed: FATAL:  sorry, too many clients already
django.db.utils.OperationalError: connection to server at "db" ... too many clients already
```

PostgreSQL's default `max_connections` is 100. The dev `web` container runs a
single Daphne process with `CONN_MAX_AGE = 0`, so every concurrent HTTP request
opens its own database connection, and the async thread pool plus the open
WebSocket consumers exhaust the pool. This is a property of the local dev stack
(one unpooled web process, one unpooled database), not of a specific view: the
failures land on `/api/widget/conversations/` and
`/api/widget/conversations/{id}/messages/` first because those are the hottest
routes.

Two load-generator effects are worth noting when reading the numbers:

- The synthetic agents do their `POST /api/tickets/{id}/comments/` synchronously
  inside the WebSocket message callback, so one k6 agent VU can only process one
  event at a time. From N = 100 on, the agent side of the test is itself a
  bottleneck, independent of the server.
- Every event is fanned out to the whole `agents.queue` group, so raising M to
  spread the replies adds server fan-out work as well.

The takeaway for production: 100–200 concurrent sockets against a single Daphne
process is where this stack needs connection pooling (`CONN_MAX_AGE` and a
pooler such as PgBouncer) and probably more than one web process. The load test
should be run again after Phase 18 moves the production image to ASGI.
